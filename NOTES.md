## Día 9 — Hecho (Registro de avance)

- Segunda sub-pestaña dentro de "Avance": `/obras/[id]/avance/registro`, junto a "Programación semanal" en `avance/sub-tab-nav.tsx`.
- Registrar avance (`src/lib/actions/avance.ts`, `createRegistroAvance`): ítem, cantidad avanzada, fecha. Mismo criterio que Gastos ([[kembron-day7-gastos]]): `usuarioId` se toma automático de `requireAdmin().userId`, nunca del form, y el `itemId` se revalida server-side contra la obra actual (`prisma.item.findFirst({ where: { id, titulo: { obraId } } })`).
- **A diferencia de Programación semanal, no se rechaza un registro que hace que lo avanzado supere la cantidad total del ítem** — es una decisión de producto, no un descuido: la consigna pide expresamente `% avance = min(100, avanzado/cantidad × 100)`, es decir, el cálculo está pensado para tolerar sobre-ejecución real (mediciones, ajustes de campo) y mostrarla capada en el reporte, en vez de bloquear el registro como sí hace la programación (que es una proyección, no un hecho consumado).

- **Problema de conectividad IPv6 con Neon**: en esta máquina, la resolución DNS del host de Neon devuelve registros IPv6 que no son enrutables en esta red. El binario nativo de Prisma para migraciones (`schema-engine`) intenta conectar por IPv6 primero, agota el timeout, y nunca llega a probar la IPv4 que sí funciona (`NODE_OPTIONS=--dns-result-order=ipv4first` no soluciona esto porque ese binario no lo respeta, al no ser un proceso Node).
- **Workaround aplicado**: se agregó una línea al hosts file de Windows (`C:\Windows\System32\drivers\etc\hosts`, requiere permisos de administrador) fijando la IP v4 del endpoint de Neon:

  ```
  18.230.255.48 ep-silent-block-ach5nlvw.sa-east-1.aws.neon.tech # added by Claude Code - force IPv4 for Neon (Kembron prueba tecnica)
  ```

- **Si se repite en otra sesión o en otra máquina** (o si el endpoint de Neon cambia de IP) y vuelve a aparecer el error `P1001: Can't reach database server`, hay que repetir este workaround: resolver la IP v4 actual del host (`nslookup <host>` y tomar una dirección IPv4) y agregar una línea equivalente al hosts file.
- El `.env` con `DATABASE_URL` (connection string de Neon) NO está en el repo (está en `.gitignore`); si se clona el proyecto en otra máquina, hay que volver a crear el `.env` a mano con la connection string real. Ahora también tiene `SESSION_SECRET` (clave para firmar las cookies de sesión con `jose`), generada con `crypto.randomBytes(32)`.
- **Usar `sslmode=verify-full` en el `DATABASE_URL`, no `sslmode=require`**: con `require` (el que sugiere Neon por default en su panel), la librería `pg`/`pg-connection-string` tira un warning de consola en cada conexión avisando que `prefer`/`require`/`verify-ca` se tratan como alias de `verify-full` y que eso va a cambiar en `pg` v9. El comportamiento real no cambia (Neon ya valida certificado igual), pero para que no aparezca el warning hay que poner `verify-full` explícito en el query string de la connection string.
- **Esta versión de Next.js (16.2.9) tiene cambios respecto a lo que es "estándar" en el entrenamiento del modelo** (ver `AGENTS.md`, que indica leer `node_modules/next/dist/docs/` antes de escribir código). Dos cambios concretos que ya pisamos:
  - `middleware.ts` fue renombrado a `proxy.ts` (mismo propósito, exporta `proxy()` en vez de `middleware()`). El archivo vive en `src/proxy.ts`.
  - El patrón recomendado para auth es Server Actions + `useActionState` (no API routes + fetch desde el cliente), con sesión en cookie httpOnly firmada con JWT (`jose`).
- **Prisma 7 con el generador `prisma-client` (el que usamos, no el clásico `prisma-client-js`) ya NO conecta solo a partir de `DATABASE_URL`**: el `PrismaClient` exige pasarle explícitamente un `adapter` (driver adapter). Para Postgres se usa `@prisma/adapter-pg`:
  ```ts
  import { PrismaPg } from "@prisma/adapter-pg";
  const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL });
  const prisma = new PrismaClient({ adapter });
  ```
  Sin esto tira `PrismaClientInitializationError`. Esto es independiente de la configuración de migraciones (`prisma.config.ts`), que sigue funcionando igual.
- El cliente generado en `src/generated/prisma` son archivos `.ts` (no `.js` pre-compilados), pensados para que los bundlee Next/Turbopack. **No se pueden correr con `node` directo** (ni con `node --experimental-strip-types`) porque sus imports internos son extensionless y dependen de resolución tipo "bundler". Para scripts one-off (ej. seed de usuarios) la opción que funcionó fue crear una API route temporal dentro de la app y pegarle con curl mientras corre `next dev`, después borrarla.
- **Con `@prisma/adapter-pg` (driver adapter), los errores de la base NO llegan como `Prisma.PrismaClientKnownRequestError` con código `P2003` (lo "clásico")**. Llegan envueltos en `DriverAdapterError` (`error.name === "DriverAdapterError"`), con el detalle real en `error.cause`. Para una violación de `ON DELETE RESTRICT` en Postgres, `cause.kind` queda en `"postgres"` (no se mapea a un kind propio tipo `"ForeignKeyConstraintViolation"`) y el código relevante es el SQLSTATE crudo en `cause.code`: `"23001"` (`restrict_violation`) — distinto del `"23503"` (`foreign_key_violation"`) que sí se usa en otros casos. Si en el futuro hay que detectar otro tipo de error de Postgres (unique constraint, etc.), conviene loguear `JSON.stringify(error.cause)` primero en vez de asumir la forma del error — la documentación de tipos (`@prisma/driver-adapter-utils`) sugiere un `kind` más específico del que realmente llega en runtime para este caso. Ejemplo del helper que quedó en `src/lib/actions/usuarios.ts`:
  ```ts
  function isForeignKeyRestrictError(error: unknown): boolean {
    if (error instanceof Prisma.PrismaClientKnownRequestError && error.code === "P2003") return true;
    if (!(error instanceof Error) || error.name !== "DriverAdapterError") return false;
    const cause = (error as { cause?: { kind?: string; code?: string } }).cause;
    return cause?.kind === "ForeignKeyConstraintViolation"
      || (cause?.kind === "postgres" && ["23001", "23503"].includes(cause.code ?? ""));
  }
  ```
- `error.tsx` en esta versión de Next recibe la prop `unstable_retry` (no `reset` como en versiones anteriores).
